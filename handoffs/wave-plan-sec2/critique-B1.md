## Verdict

go-with-changes. The shape is right (clear the column with the service role, quarantine what is ours to move, log it, restore from the log). Six things in the row are wrong or missing and would make the build fail review:
1. **Two of the five image types are not in Supabase Storage.** Club logo/banner and group photo are PRIVATE R2 keys. "Move to quarantine" does not apply; clearing the column is the whole takedown (signed URLs die in ≤1 h / ≤5 min). Reusing media-quarantine-store for them would be wrong.
2. **The log row is the only record of what was removed.** Post removal keeps `media_url` on the row; image removal clears the column. So the log insert must happen BEFORE the destructive step (or restore is impossible when it fails), and the migration must be applied BEFORE the deploy.
3. **Migration IS needed** (`moderation_actions_action_check` has no image action). Its ROLLBACK must re-add the old CHECK `NOT VALID`, because image rows can't be deleted.
4. **`ModerationAction` lives in `src/lib/auth/require-platform-admin.ts`** (the routes' import), which B1 does not own. Add it (additive union only).
5. **Scope gap: profile widget logos** (experience + working-on) are public profile images in `profiles/<uid>/logos/` or ANY external URL, 3 live. The legal copy can't say "profile" honestly without them.
6. **avatar_url may name another student's file** (me/profile accepts any URL on our host). The planner must move only the target's own files, exactly like `authorPostMediaPath`.

## Why the order has to differ from post removal

Post removal: effect → reports → log, and a failed log costs only a line, because `posts.media_url` still says what was removed. Image removal CLEARS the column, so the log row's `meta.previous` is the ONLY record of the old value (for R2 keys there is no other trace at all). Therefore:
- **Log FIRST, then act.** A failed insert = 500 "Nothing was changed." Never an unrestorable removal.
- **Finish on retry, keyed by the latest image row for that slot** (`moderation_actions_target` index on (target_type, target_id) already exists, so the lookup is cheap):
  - Remove, latest row = image_remove and current value is empty or equals `meta.previous` → finish that removal (moves are idempotent; clear is compare-and-set). No new log row.
  - Remove, anything else with a non-empty value → new image_remove row, then act.
  - Restore, latest row = image_restore → finish it (release again, set-if-empty). Restore, latest = image_remove → new image_restore row, then act.
  So a failure at any step is finished by pressing the same button again, and no action is ever unlogged. Same log-first rule for restore, or a failed restore log makes the next Remove look like a retry and go unlogged.
- **Deploy after the migration.** Old code never writes image_* so widening the CHECK first is safe; new code before the migration would 500 on every press (safe, but a broken button).
