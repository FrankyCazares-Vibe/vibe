## 2. Collisions between B1-B5, and ownership

Facts that change the plan (checked, live read-only):
- F1. Club logos/banners and group-chat photos are NOT in the `profiles` bucket. Live: orgs 1 logo + 1 banner, channels 2 photos, all R2 keys (`orgs/<org>/logo|banner/<uuid>`, group-photo prefix); 0 are https URLs. They are private R2, served only by a fresh 1-hour signed URL (`orgs/[slug]/asset/[kind]` 307s; threads sign `photo_url`). `media-quarantine-store.ts` moves between Supabase buckets only. So B1's "move to the private quarantine bucket" fits avatars/banners only. For R2 images: clear the column (compare-and-set), keep the object where it is (already private, unguessable key) as the evidence, write the key into moderation_actions.meta for restore. Access ends within the 1-hour signed-URL life, not "days". B1's cache line must say that per kind.
- F2. Club post media is R2 too: `orgs/<org_id>/posts/<uuid>` (post_media_ref_ok's org arm). The club's logo and banner live in the SAME `orgs/<org_id>/` prefix. B2's "delete a club post's files" must delete only keys under `orgs/<row.org_id>/posts/`, and only when no other posts row and neither orgs.logo_url nor banner_url names the key. Otherwise a post pointing at the logo key deletes the club's logo.
- F3. B3 can't sharp-re-encode R2 uploads: club logo/banner/post images, group photos and chat photos are presigned PUTs straight from the browser; the server never sees the bytes. Club assets go through ImageCropperModal (canvas, no EXIF). The legacy `public/html/messages.html` group-photo picker PUTs the raw file (EXIF kept, visible to chat members only). B3's sharp path = the `profiles` bucket only: `me/profile-upload` AND `lib/profile/storage-upload.ts` (`uploadProfileDataUrl`, used by `me/profile-sync` for inline data-URL avatars/banners, not in B3's owns). Defer R2 paths with that reason in the plan.
- F4. Replacing an avatar/banner happens at the COLUMN write, not the upload: `me/profile/route.ts` (PATCH mediaPatch) and `me/profile-sync/route.ts`. Neither is in B3's owns. And `parseMediaUrlField` accepts ANY https URL on our Supabase host, so a previous avatar_url can name someone else's object. "Delete the previous object" must: only remove `profiles/<self uid>/(avatar|banner)-<uuid>.<ext>`; skip it when the same URL is still in the other column; delete from `profiles` only, never `quarantine`; run after the new value is written.
- F5. Two tag normalizers already disagree: publish-post `normalizeTags` keeps Unicode letters (`/^[\p{L}\p{N}_]+$/u`, 32 UTF-16 units, 10, dedupe after lowercase); PATCH derives tags with `extractPostTags` (ASCII `[A-Za-z0-9_]{1,32}`, 10). B4's DB CHECK must accept everything BOTH emit (#café, #español), or publish 500s. Postgres regex has no \p{L}; use a code-point range or [[:alnum:]] and prove it locally with Unicode samples.
- F6. authenticated keeps INSERT/UPDATE on posts.content, tags, status (live column grants). A DB CHECK stops size/shape/duplicates but can't run the word filter, so a direct-write slur tag still reaches Trending. Fix in B4's own file: Trending drops any tag that fails checkText at COUNT time. Also posts_stamp_edited stamps only content changes, so a direct tags-only edit shows no "Edited" (report #10). B4 restates that function word for word + `or new.tags is distinct from old.tags`.
- F7. Post DELETE runs on the COOKIE client (posts/[id]/route.ts:348,384). An RLS-refused delete returns no error and 0 rows. Today the route then purges R2 video keys. With B2's tighter policies, the route must use `.delete().eq('id',id).select('id')` and purge media only when a row came back. Otherwise an officer's delete before the policy is live, or an author's delete of a removed post, says "deleted" and destroys the files anyway.
- F8. Officer delete has no button. Post menus show Delete only on the server's `is_owner` (`public/html/_postViewer.js` ~430/857, `src/components/mobile/PostViewerMobile.tsx`). B2 must add an additive `can_delete` to GET /api/posts/[id] and show Delete (never Edit) in both viewers, or the feature is API-only.
- F9. The action-log CHECK (moderation_actions_action_check) lists 15 actions, none for images, so B1's migration IS needed. target_type already allows user/org/channel. The TS union `ModerationAction` lives in `src/lib/auth/require-platform-admin.ts` (not in B1's owns). B1 adds it additively.
- F10. G3 CORRECTION: the invite-candidates removed_before / can_approve follow-up already shipped in c0b0533 (route lines 340-358, OrgInviteSheet 78-84, 511). Drop G3. And B5(b) needs no route: `POST orgs/[slug]/requests/[id]` already takes `{action:'deny'}` (and deny works across a block pair). B5 is sheet-only there.

## 3. Product: what each person will notice

**B1 image removal**
- Student: their avatar or banner is gone (initials / default gradient). Nothing tells them why. A post removal shows "Removed by Vibe moderators" on the post; a photo has no place to show it, so they'll think it's a bug and upload the same photo again. They can, instantly: removal doesn't stop a re-upload.
- Officer: the club logo or banner goes blank; any officer can put a new one up. Group chat members see the default group icon.
- Moderator: "Remove photo" on Users, Clubs and report detail, restore from the log. SURPRISES: (1) the cache line is only true for avatars/banners (public bucket, days). Club and group photos (private R2, F1) stop loading within an hour, so say that per kind. (2) An avatar_url can point at another account's file ("foreign"). The column clears but the file doesn't move, and the screen must say so. (3) Link previews already unfurled in iMessage/Discord keep their own copy; out of our reach. Add that to the moderator note, not the public copy. (4) Restore must not overwrite a photo the person uploaded after the removal: only restore into an empty column.

**B2 deletes**
- Student: deleting a photo post really deletes the file (caches still hold it for days, same as B1). A post moderators removed can't be deleted; the menu should hide Delete on it (it already shows "Removed by Vibe moderators"). Editing a caption with a filtered hashtag gets the normal content line.
- Officer: current owner/admins get Delete (not Edit) on every club post. It only exists if B2 builds the button (F8). Mods don't get it (call 8: mods moderate chat, not content). An ex-officer keeps Delete on the club posts they wrote, never Edit. Deleting the club now deletes its posts too (CASCADE); the owner's confirm line must say "Its posts, events and chats are deleted too." SURPRISE already live: an officer who deletes their own ACCOUNT takes every club post they wrote with them (posts_user_id_fkey CASCADE).
- Moderator: removed posts stay put: the author can't erase them and the club can't either (both delete policies carry `removed_at is null`). After an account self-delete, quarantined files stay; the report snapshot (reports.target_snapshot) and the action log (no FKs) survive too. SURPRISE: CASCADE on club delete takes REMOVED club post ROWS with it. The text survives in report snapshots; B2's media cleanup must skip removed posts' files.

**B3 uploads**
- Student: photos from the desktop profile composer lose their location data and look the same (`.rotate()` bakes orientation). SURPRISES to prevent: animated GIF posts must stay animated (sharp `{animated:true}`, keep format) and PNG transparency must survive (keep format; don't force JPEG). Replacing an avatar deletes the old file, so an old copied link breaks. That's intended. Video hint, plain: "Videos keep the location they were recorded at."
- Officer: nothing changes (club assets are R2 + cropper, F3).
- Moderator: SURPRISE: a person reported for their avatar can swap it before a moderator looks, and B3 then deletes the old file. The snapshot keeps only the URL. Same for B2: a reported photo post deleted before review loses its file (today the file is orphaned, not gone). See Q4.

**B4 Trending + onboarding**
- Student: a tag they spam or repeat counts once; a slur tag never trends. Publishing with a filtered tag gets the plain content line. SURPRISE: the chip tooltip says "N posts this week" (`rolling-strip-view.ts:190`, unowned). If B4 counts once per author, numbers drop and the tooltip lies. See Q5; B4 owns `tagChipTitle` + its test if the label changes.
- Re-running the old onboarding no longer resets the campus lock or the handle cooldown. Nobody should notice, since the path is legacy.
- Moderator: tags edited straight through the database now show "Edited" (F6).

**B5 follow-ups**
- Student: a deleted post shows "That's no longer available." with no Retry. Officer: can Deny a join request from the phone invite sheet, which now follows Night mode. Moderator: nothing.

## 4. Decisions for Franky (each with a recommendation)

- Q1. When a club is deleted, what happens to its posts? RECOMMEND: delete them with the club (CASCADE). Evidence: (a) the live posts_select_authenticated checks club visibility only when org_id is set. Under today's SET NULL, deleting a HIDDEN club turns its members-only posts into public personal posts for the whole campus. (b) Posts written as the club would reappear under an officer's own name, on their profile, in words they posted for the club. (c) Events, chats and memberships already go with the club (A4 ruling 8). Keep evidence: files of moderator-removed club posts are not deleted, report snapshots stay, the action log stays. Live: 0 club posts, so nothing moves today.
- Q2. Can an ex-officer delete a club post they wrote? RECOMMEND: yes, delete but never edit (edit already needs a current owner/admin, A5b). It's their writing. And their account delete already erases those posts (posts_user_id_fkey CASCADE), so refusing delete protects nothing, while edit is what enables defacing. Current owner/admins can delete any club post; mods can't (call 8). Nobody deletes a moderator-removed post.
- Q3. How long is quarantined evidence kept after the person deletes their account? RECOMMEND: keep moderator-removed files + the action log + report snapshots for 1 year from the removal, then purge. One year matches the federal preservation period for child-safety reports (REPORT Act 2024); the lawyer confirms. Until a purge job exists (post-launch), keep them and show the count on the admin screen. Only moderator-removed items are kept; everything else is deleted at once. Privacy §5 gains one sentence: "Content our moderators removed may be kept for up to a year for safety and legal reasons, even after you delete your account." B1 writes it.
- Q4. A person deletes a reported post, or swaps a reported avatar, before a moderator looks. RECOMMEND: if there's an OPEN report on that post or user, move the file to quarantine instead of deleting it. It's gone from public view either way, and the moderator can still judge it. Otherwise B2/B3 destroy the thing the report is about.
- Q5. Trending: count posts or people? RECOMMEND: rank by people (once per author per tag, as the plan says) and change the chip tooltip to "N people this week", so the number stays honest (`rolling-strip-view.ts` tagChipTitle, moves to B4).
- Q6. Tell someone when a moderator removes their photo? RECOMMEND: yes, one plain in-app line to the owner (club images: the club owner): "A moderator removed your profile photo because it broke the Community Guidelines." with the usual appeal path. Needs `notifications_type_check` widened in B1's before-deploy migration. Group photos: no notice.
- Q7. Can an owner delete a club moderators have hidden? RECOMMEND: no, "You can't delete this club right now." With CASCADE, deleting a hidden club would erase its posts, chats and events while it's under review. It's one check in the DELETE route B2 already owns.

## Final recommended approach

Verdict: go with changes. The five batches are the right cut. Fix the facts in section 2 before building: R2 images, the column-write routes, two tag normalizers, cookie-client delete, the missing officer button.

Cross-batch rules (bind B1-B5, on top of plan.md + waveA-build standing rulings):
1. **Evidence is never deleted.** No batch deletes from the `quarantine` bucket, or deletes the file of a moderator-removed item (`removed_at is not null`). Account self-delete keeps `quarantine/<uid>/**` (Q3). A file under an OPEN report is moved to quarantine, not deleted (Q4).
2. **Delete only what is provably yours and unreferenced.** `profiles/<uid>/(posts|posters)/`, `profiles/<uid>/(avatar|banner)-*`, `clips/<uid>/`, `orgs/<row.org_id>/posts/`. Before deleting, check that no other row names it: posts.media_url/media_thumbnail_url, users.avatar_url/banner_url, orgs.logo_url/banner_url. Anything else is logged and kept.
3. **Confirm, then purge.** Storage is touched only after the DB write returned the row (`.select('id')`). A 0-row RLS delete never purges.
4. **Compare-and-set on image columns.** B1 clears `where col = <seen value>`; B1 restores only into an empty column; B3 deletes the old file only after the new value is written.
5. **Cache honesty per kind:** avatars/banners "can take a few days to disappear from every cache"; club logos/banners and group photos "stop loading within an hour". Unfurled link previews are out of our reach (moderator note only).
6. **One set of tag rules.** B4's `src/lib/posts/tags.ts`, signature frozen in the plan before the build; the SQL CHECK admits every output of `normalizeTags` and `extractPostTags` (Unicode letters included); Trending re-runs checkText at count time.
7. **Migrations:** 100000 (B1) and 110000 (B2) before the deploy, 120000 (B4) after. Restate CHECK lists and policies word for word. No PRE-FLIGHT pins another batch's objects. B2 POST-CHECKs posts_update_own = `bb242564edecd0feeb551439d4ece148`.
8. **All legal/support copy is B1's.** B2 (retention sentence) and B3 (location sentence) hand their line over in their notes.
9. Shared libs additive (failure-copy, storage-purge PurgeResult, require-platform-admin union, r2.ts). Refusals never name a block. C0 tokens, Light + Night.
10. Add to plan-waveB a "Deferred, not wave B" list: user_visible EXECUTE (accepted: same answer as row visibility), channel_members settings privacy, officer event Edit/Cancel UI (recommend wave C, pre-launch), last_active_at RPC, users UPDATE grants on current_on/resume_*, unverified-reads question, Vibe+ browse-privately, crosscheck-waveA-2 decisions + follow-ups, R2 EXIF (group/chat photos), R2 GC on club/group photo replace, prod EXIF backfill run (founder-approved, after deploy), cache fix (Franky).
