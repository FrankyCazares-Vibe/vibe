## Findings (what the plan row gets wrong or leaves out)

1. **"Re-encode club logos/banners with sharp server-side" can't be done as written.** Club logo/banner/post-image bytes go browser -> R2 via a presigned PUT (orgs/[slug]/upload-url); the server never holds them. They are already canvas-cropped on the client (admin-actions.tsx:373-381, :556-560), which drops EXIF, and a cropper bypass only leaks the officer's OWN location (no victim). Recommendation: no change to R2 routes for EXIF; say so in the notes.
2. **The legacy composer needs no edit.** profile.html:6527-6531 already posts the raw file to /api/me/profile-upload kind=post; so do the two work-logo paths (:4668-4676, :9204) and ProfileMobile:1055-1070 (kind=logo, raw). Re-encoding inside profile-upload fixes all of them. Drop profile.html from B3's owns (10k-line file; Night-mode wave 5 will touch it).
3. **A second server byte path is missing from the owns list:** `src/lib/profile/storage-upload.ts:25-55` (`uploadProfileDataUrl`), used by profile-sync for the desktop's data: URL avatar/cover. profile.html:4333/:4483 skip the cropper when `window.openImageCropper` is absent, so raw bytes can arrive here too. Same helper must run there.
4. **"Replacing an avatar/banner deletes the previous object" lives in routes B3 doesn't own.** profile-upload never sees the column; the column changes in `profile-sync/route.ts` (:478-485 avatar, :630-640 banner, write loop :700-737) and `me/profile/route.ts` (:316-330, parseMediaUrlField :67-78). Add both to B3 (no other wave-B batch touches them).
5. **Naive delete = cross-user delete primitive.** avatar_url/banner_url only pass `isSupabaseHttpsUrl` (host pin, org-asset-url.ts:46). A user can set their avatar to ANOTHER user's `profiles/<B>/avatar-x.jpg`, then replace it, and a "delete the old URL" routine would delete B's photo; or point it at their own `posts/` photo and delete a live post image. Delete ONLY keys that parse as `<caller uid>/(avatar|banner)-<file>` and are not still referenced by either column after the write.
6. **Evidence: a replace can destroy a reported image.** Finding #2's abuser (intimate image as avatar) is reported, then swaps the avatar; a hard delete wipes the only copy before a moderator looks. reports (live: 0 rows; CHECKs reason_code incl. intimate_image/child_safety, status open/actioned/dismissed, target_type incl. user). Rule: if an `open` report targets this user (target_type='user', target_id=uid), MOVE the old object to `quarantine` with the existing `quarantineProfilesObjects` (same path, no edit to B1's file) instead of deleting. Also: the user-report snapshot (me/reports/route.ts:319 `id,handle,name,tagline`) records no avatar_url/banner_url, so a moderator can't tell which quarantined file was the reported one; B1 should add both columns to that snapshot (B1's report-detail work already reads it).
7. **Stale clients can point the column at a deleted object.** Once old objects are deleted, a client re-sending an older URL (stale desktop copy, a retry) sets avatar_url to a 404 and the student sees a broken photo. Guard: when an incoming own-key URL differs from the stored value, `storage.from('profiles').exists(key)`; missing -> the existing 400 "Invalid avatar_url"/"Invalid banner" (desktop `_applyAvatarAndSave` already puts the previous photo back on a refusal; phone shows its error). Also tighten the accepted value to an own `(avatar|banner)-` key (live: all 4 avatars + 3 banners already comply, 0 foreign), which removes finding 5 at the source and lets B1 assume the column is the user's own file.
8. **Race.** Read-before-write is not atomic. Do the delete from a RE-READ after the write: keys referenced before, minus keys referenced by the fresh row. Worst case left is an orphan (the pre-B3 status quo), never a deleted live photo, except two overlapping saves where one re-sends an older URL; finding 7's exists-check narrows that to milliseconds. Best-effort: log and never fail the save (same as the resume orphan cleanup at profile-sync:765-784).
9. **Decompression bombs / format spoofing.** Today the stored MIME and extension come from the client (`file.type`, route.ts:124-155) and the bytes are never decoded. With sharp: sniff magic bytes first (JPEG FFD8FF, PNG 89504E47, GIF 474946 38, WEBP RIFF....WEBP) and refuse everything else BEFORE sharp (sharp would happily render SVG/TIFF/HEIF inputs); `limitInputPixels` ~40M (animated GIF counts all frames); resize `fit:'inside', withoutEnlargement` per kind; derive contentType + extension from the OUTPUT, not the client. ## Final recommended approach

1. **`src/lib/media/strip-image.ts`** (NEW, no "server-only" so node:test can load it; imports `sharp`). Export `sniffImageFormat(buf): "jpeg"|"png"|"webp"|"gif"|null` (magic bytes: `FF D8 FF`; `89 50 4E 47 0D 0A 1A 0A`; `47 49 46 38`; `52 49 46 46 ?? ?? ?? ?? 57 45 42 50`) and `stripImage(buf, { maxEdge: number | null }): Promise<{ ok: true; bytes: Buffer; contentType: string; ext: string } | { ok: false; reason: "type" | "size" | "failed" }>`:
   - `sniffImageFormat` null -> `{ok:false, reason:"type"}` BEFORE sharp ever sees the bytes (no SVG/TIFF/HEIF/AVIF decoding).
   - `sharp(buf, { limitInputPixels: 40_000_000, animated: fmt === "gif" })` (keep sharp's default `failOn: "warning"`, which sharp recommends for untrusted input).
   - non-GIF: `.rotate()` (EXIF orientation applied then dropped). GIF: no rotate.
   - `maxEdge` set: `.resize({ width: maxEdge, height: maxEdge, fit: "inside", withoutEnlargement: true })`.
   - output in the SAME format: jpeg `{ quality: 88 }`, png `.png()` (defaults; level 9 is slow on 2560 px covers), webp `{ quality: 88 }`, gif `.gif()`. Never call withMetadata/keepExif/keepMetadata/keepIccProfile.
   - a sharp throw whose message matches /exceeds pixel limit/i -> `reason:"size"`; ANY other sharp throw -> `reason:"type"` (the bytes already passed the magic-byte sniff, so a decode failure means a corrupt/lying file; no message-regex guessing). Keep `"failed"` for nothing else than a non-Error throw. contentType/ext come from the OUTPUT format.
