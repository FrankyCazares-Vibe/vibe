## Product calls (from the critics' recommendations; Franky can override before the migrations go live)

1. **Club deletion deletes its posts** (`posts_org_id_fkey` → CASCADE), like its events and chats. A post a moderator removed is kept, detached from the club, as the record. The delete prompt says "its posts and its events". **An owner can't delete a club moderators have hidden** ("You can't delete this club right now.").
2. **Club post deletes:** current owner/admins can delete any club post; mods can't; an ex-officer can delete (never edit) a club post they wrote; nobody deletes a moderator-removed post. **Server-side only this wave** (no new Delete button; officer tools UI is a later small batch).
3. **Evidence:** moderator-removed files (the whole `quarantine/<uid>/**`) survive account self-delete, kept up to a year pending the lawyer. If someone deletes a reported post, or replaces/removes a reported avatar/cover, while a report on it is OPEN, the old file moves to quarantine instead of being deleted.
4. **Image removal (B1):** moderators can remove a user's avatar, cover, the small logos on experience/working-on entries, a club's logo/banner, and a group-chat photo. Profile-bucket files move to quarantine (older unused avatar/cover copies in that student's folder go too; a restore doesn't bring those back). Club and group images are private R2 keys: clear the column only (compare-and-set), the object stays as evidence. Log FIRST, then act; restore uses compare-and-set and answers 409 if the student set a new photo meanwhile. Only named report ids get closed. Previews on admin screens are blurred with a Show toggle. **No notice to the student this wave; no upload cooldown.** The cache note ("A removed photo can take a few days to disappear from every cache.") shows on the moderator panel only; legal pages keep the 48-hour wording (the cache fix is a must-do before the first real takedown / launch; Franky + James decide Pro vs private serving).
5. **Uploads (B3):** photos (profile photo, cover, work logos, post photos, the desktop data-URL path) are re-encoded server-side without location data; replacing a photo deletes the previous own file (or quarantines it if a report is open, call 3). Videos keep their details: both post composers show "Videos keep their original details, which can include where they were filmed." Suspended/banned accounts can't upload any photo; unverified accounts can set a profile photo, cover and résumé but not post photos. Desktop group-photo change gets the square cropper (drops location). R2 presigned uploads (club assets, chat/group photos, videos) are out of EXIF scope this wave.
6. **Tags + Trending (B4):** tags are plain `a-z`, `0-9`, `_` (0 live tags break), at most 10, no duplicates, word-filtered at publish AND edit. Trending counts **people** (once per author per tag) and the chip says "N people this week". Floor: a constant `TRENDING_MIN_AUTHORS = 1` for now (keeps the strip alive during the pilot; raise to 2 at the student launch — launch checklist). The legacy onboarding-complete and onboarding-step routes apply the restriction gate and the profile/handle word filter and can't reset the 45-day campus lock or the 14-day handle cooldown.
7. **Small follow-ups (B5):** load failures with 400/403/404/422 show no Retry (retrying can't change them). Officers can Deny join requests from the phone invite sheet (existing `{action:'deny'}` route); the row then shows "Denied". Re-inviting after a deny stays allowed. The invite sheet follows Night mode.
