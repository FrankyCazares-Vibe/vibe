## 4. Tag grammar drift (a real 500 the plan would introduce)

Six copies of "what a tag is": publish-post `TAG_RE=/^[\p{L}\p{N}_]+$/u` (:40); `extractPostTags` in `src/lib/posts/edit.ts:39` ASCII `[A-Za-z0-9_]{1,32}` (used by PATCH and, via `src/lib/composer/helpers.ts:88`, the phone composer); `public/html/profile.html:6488` `_extractHashtags`/`POST_TAG_RE`; `campus-home.tsx:6680` render regex ASCII; `CampusMobile.tsx:1189` normalizeFeedTag `\p{L}\p{N}`; feed `?tag=`.
- JS `\p{N}` includes No/Nl (½ ² Ⅻ); Postgres ICU `[[:alnum:]]` = L + Nd only. A DB rule written as `[[:alnum:]_]` would refuse a tag publish-post accepts -> the insert fails -> publish-post answers a bare 500 "Request failed" (:192-195). The helper and the DB rule MUST share one grammar.
- Every in-repo composer only ever produces ASCII `[a-z0-9_]` tags (extractPostTags / POST_TAG_RE); "#café" becomes "caf" today. Unicode tags are reachable only by calling the API directly. Unicode also opens homoglyph evasion of the word filter (Cyrillic "і" is not folded by NFKD), and Trending is exactly where an evasive tag would land.
- JS length check is UTF-16 units (stricter than PG char_length) — safe direction.

- Correction to §4: the desktop composer is NOT ASCII. `public/html/profile.html:6487` `POST_TAG_RE = /(?:^|\s)#([\p{L}0-9_]{2,32})/gu` sends Unicode-letter tags ("café"); phone (`extractHashtags` -> `extractPostTags`) and PATCH are ASCII. So today a desktop "#café" post stores `café`, and editing that post re-derives `caf`. An ASCII-only rule would silently drop desktop Unicode tags at publish (post still publishes). Franky question Q1.

## 7. The word filter misses underscore tags (measured) — "run checkText on tags" is not enough

`checkText` wraps each term in `\b…\b`, and in JS `_` is a WORD character. Measured locally against the encoded list (counts only, no term printed; scratch script, nothing in the repo): of 22 single-word terms, `checkText(term)` catches 22, `checkText(term + "_lol")` catches only 10, `checkText("lol_" + term)` 10, and `checkText("#" + term + "_lol")` (i.e. the CONTENT filter on the caption) 10. Replacing `_` with a space first catches 22/22. So:
- the tag check must be `checkText(tag)` AND `checkText(tag.replace(/_+/g, " "))`;
- the same hole exists for handles (`[a-z0-9_]`), so onboarding-step's handle check should use the same helper;
- run it over the union of the body's tags and `extractPostTags(content)`, so a direct caller who sends `#term_x` in the caption with `tags: []` is still refused.
- Accepted residue: a bare concatenation ("termlol") passes by design (the Scunthorpe guard). Trending's read-side filter has the same limit; the distinct-author floor (Q2) is the only thing that stops a solo phrase.
