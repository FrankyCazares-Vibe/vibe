## Rules every batch follows

- **Own your files.** Touch only the files your batch owns (below). If you need a change in someone else's file, write it in your notes as a request; do not edit it.
- **Notes first, in small chunks.** Start `handoffs/wave-plan-sec2/notes-<batch>.md` at once; append after every finding/decision/test (under ~40 lines per write). Keep every Write/Edit under ~150 lines; no single tool call over ~3 minutes.
- **No production writes.** Read the live database only through the read-only Supabase MCP (`execute_sql`: pg_policies, grants, function bodies, constraint defs, COUNTS; never other people's row contents). Never apply anything to production. Never push.
- **Migrations** (`supabase/migrations/<version>_<name>.sql`, version from your batch below), house format like `20260927100000_rsvp_home_campus_rls.sql`:
  header (WHY / WHAT / DOES NOT / LIVE STATE read today via MCP / apply order vs the deploy / ROLLBACK), then `begin; set local lock_timeout = '5s';` PRE-FLIGHT do-block that aborts on any drift from LIVE STATE, the change, a POST-CHECK do-block that proves it by catalog reads and, where possible, by behaviour, `notify pgrst, 'reload schema'; commit;`.
  - SECURITY DEFINER helpers: `set search_path = ''`, every name schema-qualified, `stable`, grant EXECUTE to anon, authenticated, service_role.
  - **Never `REVOKE EXECUTE` on a function** (on this Postgres image calling a function without EXECUTE crashes the backend). Grant it and refuse inside.
  - ALTER POLICY restates the old expression word for word plus the new clause.
  - Data changes to existing rows (cleanups, backfills) go in a SEPARATE file named `..._cleanup.sql` with a COUNT in the header; Franky approves those separately.
  - **Test it on the local database**: `docker exec -i supabase_db_vibe psql -U postgres -d postgres < file`, then exercise it as real roles (`set local role authenticated; select set_config('request.jwt.claims', '{"sub":"<uuid>","role":"authenticated"}', true);`) inside a transaction you ROLLBACK. Record each probe and result in your notes. Seed users: blake `6979e030-690b-4092-bb91-fd6f00a6a988` (IU), casey_purdue, drew_new, avery owner; read ids from the local `public.users`.
- **The route must never allow what the policy refuses** (the user gets a 500 instead of a clean answer). When you tighten a policy, find every caller (grep `from("<table>")`) that writes with the cookie client and make sure it still works or answers cleanly.
- **Blocks:** reuse the existing helpers (`is_blocked_either_way` in SQL; `loadPairBlock`, `isBlockedWithOrg`, `loadHiddenUsers` in TS). Don't invent a second block model.
- **Admin flag** is service-role only (`createSupabaseServiceClient()`); a cookie-client read returns nothing, silently.
- **Tests**: pure logic goes in a small `src/lib/**` module with a `*.test.ts` beside it (node:test + node:assert, like `src/lib/moderation/reports.test.ts`). Run `npm test` (node --test, NOT vitest) and `npx tsc --noEmit -p .`. Known pre-existing failure: `src/lib/otto/parse-reminder.test.ts`.
- **UI**: colours only via the C0 tokens (`var(--charcoal)`, `var(--paper)`, `var(--hairline)`, ...; never `var(--muted|accent|border)`); must read in Light and Night. Plain-English copy, no jargon.
- **Return** a structured summary: files changed, migrations written (+ order vs deploy), local test results, anything left for someone else, open questions for Franky.
