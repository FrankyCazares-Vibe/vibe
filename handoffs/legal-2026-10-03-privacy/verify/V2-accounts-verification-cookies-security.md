# V2: accounts, verification, cookies, security, consent record

Checker 2, 2026-10-03. Text checked: `privacy-policy-v2.md` sections 2, 3a, 7, 10 and 13.
Code read: LAND (`landing-night`, commit 21af1a5) for everything, MAIN compared where the two differ (only the sign-up page, `api/me/route.ts`, `proxy.ts` and the admin gate differ in this area).
Paths are relative to the repo root. `ssr/` means `node_modules/@supabase/ssr/dist/main/`, `auth-js/` means `node_modules/@supabase/auth-js/dist/main/`.

**Result: 60 sentences checked. 48 confirmed. 12 need a change: 1 wrong, 8 overstated, 1 unsupported, 2 risky wording. 7 things are missing (end of file).**

The ones that matter most:

1. **V2-6 (wrong).** The order of the sign-up steps. A new account accepts the Terms with the tick at sign-up, before the email is confirmed. There is no separate "accepts the Terms" step after it.
2. **V2-24 (overstated).** The starter display name (the part of the sign-in email before the @) is open to anyone with the profile link, signed in or not. The policy says "signed-in users".
3. **V2-43 (overstated).** Two "Sign out" buttons sign out this browser only. And other devices can keep working for up to an hour.
4. **V2-10 (overstated).** "We do not record the date" of verification. The email log keeps the time each verification email was sent, tied to the account.
5. **V2-50, V2-53 (risky wording).** "No two-factor for the admin accounts" and "the sign-in cookie can be read by scripts" are true and hand an attacker a plan.

## MISSING: things the code does in this area that the policy does not say

1. **The school-verification link carries your school address and account id in readable form.** The token in `/auth/verify-school?token=...` is the address, the account id and an expiry, base64-encoded and signed, not encrypted (`src/lib/auth/school-email-token.ts:25-27`, `:46-60`; link built at `src/app/api/auth/school-email/request/route.ts:246`). Anyone who sees the link can decode it, and section 6 already says Vercel's request logs keep the address requested. The page moves the token out of the address bar after it loads (`src/app/auth/verify-school/page.tsx:38-45`), but the first request is logged. The link works for 48 hours. Suggested sentence for section 3a or 6: "The link in the verification email contains your school address and account id, so our host's request log sees them when you open it."

2. **The access code arrives in the sign-up link.** The invite email's button opens `/auth/signup?access_code=VIBE-...` (LAND `src/lib/waitlist/email-content.ts:94`, `src/app/auth/signup/page.tsx:38-41`). The page strips it from the address bar after load (`signup-form.tsx:183-188`), but Vercel's request log sees it first. Section 3d says Sentry strips access codes; nothing says the host log holds them. The code is single-use, so the risk is small; the sentence is about completeness.

3. **What an unverified account CAN do.** Section 2 lists what it cannot do. The code lets it like, save, follow people and clubs, edit its profile and file reports (`src/lib/moderation/access.ts:19-27`; `src/app/api/posts/[id]/like/route.ts:75`, `src/app/api/orgs/[slug]/follow/route.ts:69`). A like sends the author a notification naming the liker, and before set-up that name is the front half of the sign-in email (V2-23). It cannot join a club (`src/app/api/orgs/[slug]/join/route.ts:176-179`).

4. **An account that never confirms its email cannot delete itself.** Delete lives behind sign-in (`src/app/api/me/route.ts`), and with email confirmation on there is no session until the address is confirmed. Such an account, with its sign-in email and the starter name made from it, stays until its owner confirms and deletes it or writes to help@connectvibe.app. Section 3a says it "is kept until someone deletes it" but not that the owner has no button.

5. **Sign-up details also sit in Supabase's sign-in record and in your session token.** The Terms version, the 18+ flag and a hash of the access code are stored in the sign-in record's metadata and copied into every session token (`signup-form.tsx:290-294`; `supabase/migrations/20261003130000_waitlist_code_scrub.sql:4-22`). The typed access code itself is in the first session's token, in the browser of the person who typed it (`same file:19-22`). Section 13 describes only the acceptance table.

6. **A breached-password check may run at Supabase.** The sign-up form has copy for "That password has shown up in a data breach" (`signup-form.tsx:66-67`, `:92`). That answer comes from Supabase's leaked-password check, which, when switched on in the dashboard, compares part of a hash of each new password against the Have I Been Pwned list. Section 6 does not name that service. [NOT VERIFIED: whether the switch is on in production. It is a dashboard setting.]

7. **The second cookie and the worker script.** Section 7 names one cookie precisely and the other only as "short-lived" (V2-33). It also says the site keeps "one file", the offline page; the browser also keeps the small worker script that serves it (`public/sw.js`, registered in `src/components/pwa/ServiceWorkerRegistrar.tsx`). Neither holds personal data, so this is a wording gap, not a privacy one.
