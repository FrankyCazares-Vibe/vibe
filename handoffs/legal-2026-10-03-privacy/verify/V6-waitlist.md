## MISSING

Things the code does, that a person on the waitlist would want to know, and that the policy does not say.

1. **Founders see which account you made.** Once your code makes an account, the founders' list shows "Joined as @yourhandle" on the same row as your name, masked school address and answers, until the entry is deleted. Evidence: `store.ts:403-411` (reads the handle), `admin-view.ts:142`, `src/app/admin/waitlist-rows.tsx:49-51`. Section 11 says only "next to your name and answers".

2. **A reply to a waitlist email shows your full address, with no log and no 40 days.** Both emails set reply-to `hello@connectvibe.app` (`email-content.ts:46`; `resend-transactional.ts:308`), and the copy asks people to reply ("Questions, or the code stopped working? Reply to this email." `email-content.ts:192`; "Reply to your invite email and we'll send you a new one." `confirm-client.tsx:56`; two `mailto:help@` links at `confirm-client.tsx:20-21`). A reply lands in the founders' inbox with the full address. That sits outside the masked list, outside the logged reveal, and outside the 40-day clean-up. Section 11 says it "stands on its own", so it should say this in one line and point to section 3g.

3. **The entry holds more than the answers.** Not listed under "What we collect": which wording of the form notice you agreed to (`notice_version`, `store.ts:183`); when the confirm email went and when you confirmed (`100000:191-192`); the wave name; when a code was sent, when it ends and how many were sent; the id of the founder who sent it or added you (`100000:195-203`); and the state a new code replaced, kept so a failed send can be undone (`code_prev`, `120000:118-120,389-393`). Link tokens and codes are stored only as SHA-256 hashes (`100000:189-194`). One sentence would cover it: "and the state of your entry: when we emailed you, when you confirmed, your wave, when a code was sent and by which founder."

4. **An entry can exist for an address whose owner got no email, or never asked.** The form stores an entry before anyone confirms (`route.ts:136-137`), and anyone can type anyone's school address. When the day's confirm-email allowance is spent (30 a day by default, `admin-view.ts:157`; 10 a day per network, `route.ts:27`) the entry is saved and no email is sent (`route.ts:63-66,135-141`), while the page still says "Check your school inbox". That person has no "Take me off the list" link. The entry goes after at most 30 days, but "Leaving sooner" offers only the email link. Add a second way: "or write to hello@connectvibe.app from that address."

5. **The news tick does not outlive the entry.** See V6-12. If a news email is ever built, the list of people who ticked is gone 40 days after each joined.

6. **The sign-up page, not the form, can show whether an address has an account.** While sign-up is closed, the sign-up endpoint answers a new address with "access code required" and an existing one as it always has. The migration records this as known and accepted (`120000:42-47`). V6-35 is true of the form, but a reader will take it as "nobody can find out who has an account". Either drop "or who has an account" or add "through this form".

7. **The link token and the access code travel in web addresses.** The confirm and leave links carry the token as `?token=` (`email-content.ts:81-83,89-91`) and the "Create your account" button carries the code as `?access_code=` (`email-content.ts:98-102`), so Vercel's request logs see both. The code avoids this for its own API calls (`status/route.ts:18`), strips both from Sentry (`sentry-config.ts:16-17`), removes the code from the address bar after load (`signup-form.tsx:185-186`), and sends no Referer from the confirm page (`src/app/waitlist/confirm/page.tsx:7-11`). Section 6 already says Vercel sees "the address requested"; one clause in section 11 would close the gap.

8. **The plain access code sits in your first sign-in token.** The database replaces the code with its hash, but the first session's token, built before that, still carries the code as typed, on your own device, until it is refreshed (`130000:20-22`). The code is already used by then. Low importance; listed for completeness.

9. **People added by hand never ticked the waitlist boxes.** A founder-added entry has no age tick and no "Email me" tick (`100000:208-210`; `add/route.ts:24-27`): the person asked a founder directly. Section 11 says they are added "for example a club officer who wrote to us", which is the basis, but does not say the first email (the access code) goes without the tick. They do tick 18+ at sign-up.
