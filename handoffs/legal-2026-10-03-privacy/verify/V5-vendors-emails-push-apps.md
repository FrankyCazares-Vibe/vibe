## The one that matters most

**V5-10. The sign-in cookie is not stripped from server error reports.** The policy says "we never attach your account id or email, and we strip sign-in tokens". Vibe's scrubber only rewrites tokens that sit in a web address or a request body. When server code fails, the Sentry SDK attaches the request's headers, and that includes the Cookie header. The Supabase sign-in cookie holds the access token, the refresh token, the account id and the sign-in email. I ran the scrubber on a fake event: the cookie came out untouched. Either fix the code (drop `request.cookies` and the `cookie` header in `beforeSend`) or change the sentence. Fixing the code is a few lines and is the better answer.

## MISSING

Things the code does in this area that a user would want to know and the policy does not say.

1. **What a Sentry report really carries.** The table gives Sentry one line. Vercel and Google get "your IP address and browser"; Sentry does not, though the browser connects to it directly (no tunnel, `next.config.ts:128-133`) and every browser report includes the browser's name and version and the page address. Server reports carry the request's headers (see V5-10). The SDK drops the usual IP headers (`node_modules/@sentry/core/build/cjs/vendor/getIpAddress.js:3-16`), but anything else the host adds to a request stays. Vercel's documentation says it adds headers with the visitor's city, region and coordinates worked out from the IP address, and one named `x-vercel-proxied-for`; none of these is on the SDK's drop list. I could not check a live event. If they do arrive, section 3e's "we never work it out from your IP address" is still true of Vibe's code, but Sentry would hold an approximate location. Open one recent server event in the Sentry dashboard and look at its headers before publishing. Suggested table text: "Error reports and a 10% sample of performance traces. Sentry sees your IP address and browser, the page address, and for a failed server request the request's headers."

2. **A failed email leaves the provider's error text in our log.** Up to 500 characters, addresses blanked (`src/lib/email/send-log-core.ts:177-187`, `email_sends.error_message`). Folded into the correction for V5-6.

4. **"No AI vendor" is true of the app, not of how it is built.** The migrations record that the live database is read through an AI coding assistant's database tool ("The Supabase MCP execute_sql is read-only", `supabase/migrations/20260911100000_channel_members_delete_own_pending.sql:34,48`; "LIVE STATE, 2026-09-21 (read-only MCP)" in `20260922104000_email_sends.sql:49-60`). The short version's "no AI vendor" and 3c's "Nothing goes to an AI company" read as absolute.
