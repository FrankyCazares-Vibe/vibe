### T1 · Close the six world-readable tables (likes, comment likes, reposts, follows, events, RSVPs)

**In plain English.** Any signed-in student can today ask the database directly (the public
REST endpoint, with the app's public key and their own login) for every like, comment like,
repost, follow edge, event and RSVP on Vibe, with who did it and when. The app's screens only
show counts and a few lists, but the tables themselves are wide open. T1 narrows each table to
"your own rows" (plus the few extra rows a real screen needs), moves every count to small
database functions that return numbers only, and moves the handful of lists that show other
people (someone's followers, someone's reposts, friends who reposted) to server-side reads that
run after a block check. No screen changes shape. The product line holds: counts are public,
identities are private.

- Defined at `supabase/migrations/20260504130000_post_likes_comments.sql:30-33`,
  `20260508120000_comment_likes_and_replies.sql:27-30`, `20260508100000_post_reposts.sql:30-33`,
  `20260430190000_phase1_initial_schema.sql:306` (connections), `:463` (events), `:480` (rsvps).
- **Table grants (pg_class.relacl, all six identical):** `anon`, `authenticated`, `postgres`,
  `service_role` each hold `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER,
  MAINTAIN`. No anon policy exists, so anon reads 0 rows today, but the grants are wider than any
  caller needs. (information_schema.role_table_grants shows 0 rows to the MCP role; use relacl.)
- No view and no function body reads these tables. Only SECURITY DEFINER triggers touch them:
  `trg_notify_on_like` (post_likes), `trg_notify_on_connection` (connections). None is in the
  `supabase_realtime` publication. No `(count)` embeds of these tables exist anywhere.
- Helpers the design leans on (all SECURITY DEFINER, STABLE, `search_path=public`, EXECUTE to
  authenticated + service_role): `is_org_member(oid,uid)`, `org_member_role(oid,uid)`,
  `has_recorded_consent()`. `org_members.role` ∈ owner/admin/mod/member; "officer" means
  owner or admin everywhere (matches `org_followers_select`).
- `orgs_select` is `(is_public OR member) AND (hidden_at IS NULL OR member)` and the only real
  club is `is_public = false`, so any events policy that joins `orgs` under the viewer's RLS
  would hide that club's rush events from every non-member. The events route already works
  around this with service reads (`src/app/api/events/route.ts:94-111`). The new policy uses a
  SECURITY DEFINER helper for the same reason.

-- Policy helper: can the caller see this event? Creator, OR club not hidden (private clubs
-- included: rush events are public on purpose), OR member of the (hidden) club, OR has an
-- RSVP on it. DEFINER so it can read orgs/org_members/rsvps without the caller's RLS.
create or replace function public.event_visible(p_org_id uuid, p_creator_id uuid, p_event_id uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select coalesce(p_creator_id = auth.uid(), false)
      or (p_org_id is not null and exists (
            select 1 from public.orgs o
             where o.id = p_org_id
               and (o.hidden_at is null
                    or exists (select 1 from public.org_members m
                                where m.org_id = o.id and m.user_id = auth.uid()))))
      or exists (select 1 from public.rsvps r
                  where r.event_id = p_event_id and r.user_id = auth.uid());
$$;

-- Policy helper: does the caller manage this event? Creator, or owner/admin of its club.
-- Same rule as events/[id]/attendees/route.ts:53-65.
create or replace function public.can_manage_event(p_event_id uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from public.events e
     where e.id = p_event_id
       and (e.creator_id = auth.uid()
            or (e.org_id is not null and exists (
                  select 1 from public.org_members m
                   where m.org_id = e.org_id and m.user_id = auth.uid()
                     and m.role in ('owner', 'admin')))));
$$;

-- Count RPCs. Numbers only, never identities. Each re-applies the visibility rule of the
-- thing being counted, so it answers only for posts/comments/events the caller can see.
create or replace function public.post_engagement_counts(p_post_ids uuid[], p_since timestamptz default null)
returns table (post_id uuid, like_count integer, repost_count integer)
language plpgsql stable security definer set search_path = public as $$
#variable_conflict use_column
begin
  if coalesce(cardinality(p_post_ids), 0) > 1000 then
    raise exception 'too many ids (max 1000)' using errcode = '22023';
  end if;
  return query
    select p.id,
           (select count(*)::int from public.post_likes l
             where l.post_id = p.id and (p_since is null or l.created_at >= p_since)),
           (select count(*)::int from public.post_reposts r
             where r.post_id = p.id and (p_since is null or r.created_at >= p_since))
      from public.posts p
     where p.id = any(p_post_ids)
       and (p.status = 'published' or p.user_id = auth.uid());   -- mirrors posts_select_authenticated
end $$;

create or replace function public.comment_like_counts(p_comment_ids uuid[])
returns table (comment_id uuid, like_count integer)
language plpgsql stable security definer set search_path = public as $$
#variable_conflict use_column
begin
  if coalesce(cardinality(p_comment_ids), 0) > 1000 then
    raise exception 'too many ids (max 1000)' using errcode = '22023';
  end if;
  return query
    select c.id, count(cl.user_id)::int
      from public.post_comments c
      join public.posts p on p.id = c.post_id
      left join public.comment_likes cl on cl.comment_id = c.id
     where c.id = any(p_comment_ids)
       and (p.status = 'published' or p.user_id = auth.uid())

end $$;

create or replace function public.event_rsvp_counts(p_event_ids uuid[])
returns table (event_id uuid, going_count integer, maybe_count integer)
language plpgsql stable security definer set search_path = public as $$
#variable_conflict use_column
begin
  if coalesce(cardinality(p_event_ids), 0) > 1000 then
    raise exception 'too many ids (max 1000)' using errcode = '22023';
  end if;
  return query
    select e.id,
           (count(r.id) filter (where r.status = 'going'))::int,
           (count(r.id) filter (where r.status = 'maybe'))::int

     where e.id = any(p_event_ids)

-- "N you both follow" per candidate: how many of the candidate's followings the CALLER also
-- follows. Same math as lib/connections/queries.ts hydrateUserCards. Rows only where N > 0.

#variable_conflict use_column

    raise exception 'too many ids (max 1000)' using errcode = '22023';
  end if;
  return query
    select c.follower_id, count(*)::int
      from public.connections c
     where c.follower_id = any(p_user_ids)
       and exists (select 1 from public.connections v
                    where v.follower_id = auth.uid() and v.following_id = c.following_id)
     group by c.follower_id;
end $$;

-- those mutuals follow each one. Excludes the caller. Optional p_among narrows the answer.
-- Top 1000 by via_count, a deliberate ordered cap (PostgREST max_rows = 1000 would
-- otherwise truncate silently).

returns table (user_id uuid, via_count integer)

#variable_conflict use_column
begin

    raise exception 'too many ids (max 1000)' using errcode = '22023';
  end if;
  return query
    with mine as (
      select o.following_id as mid
        from public.connections o
       where o.follower_id = auth.uid()
         and exists (select 1 from public.connections i
                      where i.follower_id = o.following_id and i.following_id = auth.uid()))

      from public.connections c
     where c.follower_id in (select mine.mid from mine)
       and c.following_id <> auth.uid()
       and (p_among is null or c.following_id = any(p_among))
     group by c.following_id
     order by count(*) desc, c.following_id
     limit 1000;
end $$;

#### Risks
1. **Order is the whole game.** File 2 on prod before the T1 code is live gives zeros on every
   like, repost and going count, and follow lists that show only yourself: the "tightened a
   SELECT, screens went quiet" bug. Apply file 2 only after Vercel shows the T1 deploy Ready,
   and compare against the pre-flight snapshot. The same applies in reverse: an instant
   Vercel rollback to a pre-T1 build while file 2 is live has the same effect, so run file 2's
   ROLLBACK first (a few seconds, restores the open policies).
2. **Service reads in the list, reposts and friend-reposter paths** return other people's
   edges if a filter is wrong. Each one filters on explicit ids, runs after a block or follow
   check, and selects only id and timestamp columns. The adversarial reviewer should read
   exactly those five call sites. If `SUPABASE_SERVICE_ROLE_KEY` is missing, `feed` must skip
   friend reposters (use `isSupabaseServiceConfigured()`, log, empty map) rather than 500.
3. **DEFINER helpers are callable directly over REST.** `event_visible` takes arbitrary ids,
   so a signed-in caller can learn whether a given club UUID is hidden. UUIDs are unguessable
   and the same fact already leaks through `/api/events?org_id=`. Accepted. `can_manage_event`
   and every count RPC answer only about the caller or return numbers.
4. **Behavior changes that are intended, but new:** club-less events (0 live) now show only to
   their creator and RSVP holders. The profile Reposts tab and the three follow lists now
   return empty between blocked pairs. The three follow lists now answer 500 on a failed read
   instead of an empty list (`profile.html` already paints Retry for a failed first page,
   `:10112`). Suggestions' friend-of-friend signal is now a deterministic top 1000 instead of
   an arbitrary 1000 rows.
5. **Residual leak outside T1:** `search/route.ts:146-150` resolves campus club ids with the
   service client and no `hidden_at` filter. After T1 only members of a hidden club can see
   its events in search (today everyone can). One-line follow-up for the search owner:
   `.is("hidden_at", null)`.
6. **Performance:** `event_visible` runs per event row and `can_manage_event` per RSVP row. At
   10 and 6 rows that is nothing. If events grow past a few thousand, add
   `events(org_id)` and `org_members(user_id, org_id)` indexes. The count RPCs replace
   row-fetch-then-count, so they also remove today's silent 1000-row truncation in the feed,
   comments and hydrate paths.
7. **Product question, not blocking:** follow lists stay visible to any signed-in, unblocked
   student (today's behavior, Instagram-like). If Franky wants them private or paid, only the
   four list routes change. The table policy is already narrow.
8. **Local vs prod drift:** the seed writes `users.campus_id` and `handle` as `postgres`. If
   `users_campus_in_system` or a handle guard rejects it locally, fix the seed. Never loosen
   a trigger to make a seed pass.
