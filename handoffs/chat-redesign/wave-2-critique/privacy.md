## Verdict

**Buildable after the changes below; one HIGH.** The privacy model of the draft is sound: counts stay public and identities stay private everywhere the NEW code reads (voters, going, snapshots, anonymous polls, the side tables with no policy). The stub's shape is safe for every consumer I could find. The officer-Board-post exception is Franky's Sept 29 call, narrowed in three defensible ways the draft already lists as open point 14.1. D2 (no policy change in v1) is defensible and its after-launch clause is exact.

What fails is the one place the draft itself says Block "must hold wherever the reviewer looks" (8.6) and then leaves untouched: **the OLD inbox's club-room preview** (`GET /api/me/threads`, flag off — exactly what Apple's reviewer sees on Oct 16) is read with no block filter and shows a blocked person's last message under the club's row. One MEDIUM: poll and sign-up voters are read with the service role, so a restricted account's name shows in a card where every other surface hides it.

Counts: **1 HIGH, 2 MEDIUM, 8 LOW.**

**The top changes**

1. **Filter the old inbox's club-room previews by the viewer's block set** (H1): `threads/route.ts` already loads `hiddenRes.hidden.blocked` (`:716-721`); pick the newest of the 5-row window whose author is not in it. Add the file to W2-B3's row in 13.2 and a row to 8.3. Add the case to the Mac walk.
2. **Read voters' `Person`s on the viewer's cookie client, not the service role** (M1), as `readGoing` does (`message-read.ts:896-906`); a person the viewer cannot read is left out of `voters` and counted like a blocked one.
3. **Never quote a blocked person, no Board exception for `parent_preview`** (M2): drop the exception from 8.3's second row so the nulling needs no role lookup for a parent that is not in the page.
4. **Pin the small copy and walk items** (L1–L8): the "officer" sentence for a mod's removal, the stub reported by id, the `(select auth.uid())` form in the D2 clause, the sign-up row with a hidden taker, the empty reply fold, the 14.1 wording, the Mac walk's block cases, the old renderers filtering the array rather than the bubble.

Severity: **HIGH** = built literally it breaks something, leaks something, or a batch cannot finish. **MEDIUM** = real rework, a missed file, a payload a screen cannot use. **LOW** = wording to pin.

## Holds (checked against the repo and the decisions; no change needed)

1. **The stub's shape (8.1) is safe for every consumer found.** `user_id: ""` matches no viewer (`isMine = m.user_id === meId`, `MessagesMobile.tsx:1814`; `campus-home.tsx:16392`) and no author; `users: null` is already a legal value (TY:243); `content: ""`, `reactions: []`, `card: null`, `removed: null` are today's defaults; `kind: "text"` on every stub means a hidden card's kind is not named; `id`, `created_at`, `thread_root_id` keep `?after=` / `?root=` paging and the every-5th drop rule stable (9.3). The mini messenger keeps `hidden` in its map and skips at draw (12.1). The type needs no change.
2. **What a stub lets the viewer infer is already public to them.** Existence and time of a hidden message (the stub), a count larger than the names (votes, going, replies, unread) all say "someone here is in a block pair with me". The app already tells the blocked side exactly that, and who, on the profile (`bootstrap/route.ts:205-232`: `blockedByTarget` → "This account has restricted you"), so the stub adds no new disclosure. The /plus page's promise "no seeing who blocked you" (`src/app/plus/page.tsx:712`) is about a list, not this.
3. **Blocked people are out of `voters`, `going` and the "first 8"** (5.2 voters minus `blocked`; 8.3 `readGoing` per-step filter with the next member taking the place; `voters_more` never counts a blocked person). Counts unchanged, as Franky said. Plumbing is ROUTES-M5's.
4. **The officer-Board-post exception is Franky's** (W0 evening call: "an officer's Board post shows to every member, so nobody misses club news") and the draft carries it in 8.2, 7.1.4 (inbox preview), 7.2.4 (`board_latest`) and 8.4 (the name shows) consistently; L7 only asks 14.1 to spell out the narrowings.
5. **D2 is defensible.** Before the block both people could read each other (`messages_select_org_member`, DM:7); the app's only readers are the routes; the B1a security review proved the direct-read gap and named the clause (F6b, `B1a-review-security.md:67-68`); the draft's 8.7 clause is DM:7's word for word, callable from a policy under `authenticated` because the first argument is the caller (`is_blocked_either_way`, DM:5.1). Apple tests the app, not PostgREST. L3 asks only for the initplan form and the own-row note.
6. **Anonymous polls hide names from everyone, the creator and officers included.** 5.2 `voters: []` when `anonymous` regardless of the viewer's role; `voters_more: 0`; `options[].mine` is the viewer's own pick only; the snapshot (5.3) carries no people; the side tables have no policy and `revoke all` (3.1, DM:6.2) so no direct read exists; no edit route can flip `anonymous` after creation (3.1 "No edits in v1"). A sign-up is forced `anonymous = false, multi = true` by the RPC and the CHECK (3.1, 3.3) — Franky's d/10. "Counts from the first vote" is accepted (wave-1 12.8).
7. **Sign-ups show names to room members only.** `hydrateCards` is given only rows from a viewer-scoped read (5.2, wave-1 contract 5); the Officers room is reachable only through `can_view_org_channel`'s allow-list arm (DM:3.6); an event room past its window stays readable by its row-holders and officers (no time test in the event arm, DM:3.6) — read-only, names still shown, consistent with 11.6. A withdrawn RSVP or a leave deletes the row AND the person's votes (3.5 `chat_votes_drop_access`), so their name leaves the sign-up; the accepted gaps (Officers room has no rows; a private `room`) are written in 3.5.
8. **The report snapshot has no voter names** (5.3 "No voter names, no ids of people"; wave-1 contract 5); `snapshotCard` runs after `readTarget` proved the reporter can read the message (`reports/route.ts:291-301` on the reporter's client), so the service-role read adds nothing the reporter could not see; the snapshot never returns to the reporter (L2). Student text staying in the database is the documented design (DM:5.7).
9. **A removed message's card**: not hydrated (5.2, 6.1); the author sees `removed` with `card: null` and the card (6.2); everyone else loses the row by RLS. Votes stay in the side tables (harmless: nothing reads them for a removed message; the sender's hard delete cascades them, 6.1.2).
10. **The remove route's rank rule vs Franky's call 27.** Franky: "owners, admins and mods can remove … soft remove, never on a message with an open report". The rank rule is the wave-1 contract's kept default (12.3) and the contract is FINAL; 6.1 runs the role check before `outranks` (14.10), the open-report check against `status = 'open'` (DM:5.7 `reports_status_check`), and never hard-deletes. A mod cannot read the Officers room, so step 2 finds no row and step 7 answers 404 for a live message there (`removed_at` null with no cookie row).
11. **`RemovedContentCard` for an officer's removal**: no appeal link is a product call (D9) and no Apple rule needs one; "Only you can see this message." is true by the SELECT policy (`(removed_at IS NULL) OR (user_id = auth.uid())`, DM:7). The moderator copy is unchanged (`ReportSheet.tsx:658-716`). L1 is copy only.
12. **Reactions carry no names** (`ReactionGroup = { emoji, count, viewer_reacted }`, `reaction-emoji.ts:48-52`), so a blocked person's reaction on a visible message reveals nothing (8.4); the direct-read restatement of `message_reactions_select_member` is listed for the after-launch file (8.7).
13. **Mentions by a blocked person in a club room** write a notification row (`messages/route.ts:545-590`, no block test at insert) but never reach the viewer: `/api/me/notifications` filters through `loadHiddenUsers` (`notifications/route.ts:6, 72`) and push skips blocked actors (`push/dispatch.ts:633`). Card text is not parsed for mentions (4.1.7). Unchanged by wave 2.
14. **A send into a club room is not refused by a block** (8.5): `messages/route.ts:415-431` skips `dmSendBlocked` for org channels on purpose ("one block shouldn't silence a whole community channel"); both keep posting, each stops seeing the other. Matches Franky's "both ways".
15. **The Apple walk, flag ON**: Block → the club chat (stubs) → a poll by the other (a stub; the viewer's own poll shows the other's vote in the count only) → "who's going" (the other left out, the count unchanged) → the other's profile ("restricted you"). Flag OFF: the same minus cards, plus H1.
16. **`eventRefsFor` and the Event card show counts only** (`going_count`, `maybe_count`, `viewer_status`), never a going list — Franky's call b ("outside the room it stays counts only"); the going list exists only on `ThreadRoom.event`, inside the room, room members only (`readGoing`, `message-read.ts:872-879`).
17. **The old phone sheet hides `Group info` for a club room** (`MessagesMobile.tsx:2382`), so no roster is reachable from the old inbox; wave-1 B5 hid Leave / + Add / rename there (wave-1 contract 10.3).
18. **`chat_votes_drop_access` is privacy-positive**: a person who leaves, is removed, or withdraws an RSVP takes their votes (and their name on sign-ups) with them; account deletion cascades `chat_poll_votes.user_id` and `chat_polls.created_by` (3.1).
