# Fact-check: web-android-push.md

Checked 2026-09-24 against primary sources: Chrome/web.dev, MDN and `@mdn/browser-compat-data` 8.1.2 (2026-09-17), chromestatus.com, chromiumdash, the RFCs, the W3C Push API ED, webkit.org, developer.apple.com, nextjs.org, vercel.com, the npm registry (`npm view`), the published `web-push@3.6.7` tarball, and the GitHub API.
The research file was not edited.

**Result: 51 claims checked. 39 CONFIRMED, 11 CORRECTED, 1 UNVERIFIED.**

## Corrections that change what we build (read these first)

1. **Put `app_badge` inside `notification`, not at the top level.** In WebKit's shipped format (webkit.org/blog/16535, 2025-03-27), `"app_badge"` sits *inside* the `notification` object (their example uses `"app_badge": "1"`). The W3C Push API ED doesn't define `app_badge` at all. Only the obsolete WebKit explainer, which used a different `title`/`options`/`default_action_url` shape, had it at the top level. `mutable` *is* top-level (W3C ED). **Fix the checklist item 6 payload** to `{"web_push":8030,"notification":{...,"app_badge":N},"mutable":false}`, and have our own SW read `notification.app_badge`.
2. **`Content-Type: application/notification+json` cannot be set through web-push 3.6.7's `headers` option.** The library copies `headers` first and then sets `Content-Type: application/octet-stream` whenever there is a payload (`src/web-push-lib.js`, `generateRequestDetails`, right after the `extraHeaders` copy). The header is silently overwritten. The spec doesn't need it, so drop that line; don't plan on it.
3. **Handle 401 as well as 403.** RFC 8292 §4.2 says "A 401 (Unauthorized) status code might be used if the authentication is absent; a 403 (Forbidden) status code might be used if authentication is invalid." Mozilla autopush documents **401 "Bad Authorization - Authorization header is invalid or missing"** (errno 109), https://mozilla-services.github.io/autopush-rs/errors.html. Firefox VAPID or config errors therefore come back as **401**, not 403. The sender's status map (section 6 item 5) must treat 401 like 403 (config alert, don't delete the row).
4. **`clients.openWindow()` does not refuse cross-origin URLs.** MDN (modified 2026-09-12) says the promise "resolves to a WindowClient object if the URL is from the same origin as the service worker or a null value otherwise". A cross-origin URL can still open; we just get `null` back. **Our own same-origin validation of `data.url`/`navigate` in the SW is the only guard.** Keep it mandatory.
5. **The install origin trials are over or ending, and both APIs are now slated to ship on desktop.** chromestatus: Web Install API (`navigator.install()`) OT ran desktop **143–148, extended to 150**. Chrome 150 went stable 2026-06-30, so the OT is past. The `<install>` element OT was desktop **148–153**, and Chrome 154 is stable as of 2026-09-22. **Both have an Intent to Ship targeting Chrome 156 desktop** (blink-dev, 2026-09-21; Chrome 156 stable is scheduled for 2026-10-20 per chromiumdash). Android comes "later". The recommendation still holds: ship `beforeinstallprompt`, because Android is what matters. But "origin trial, needs tokens" is stale. `<install>` may be usable on desktop without a token right around launch. Sources: https://chromestatus.com/feature/5183481574850560, https://chromestatus.com/feature/5152834368700416, https://www.mail-archive.com/blink-dev@chromium.org/msg17503.html.

## Corrections to sourcing or labels (build impact small)

6. **"Chrome ignores empty fetch handlers" was marked UNVERIFIED. It is verified.** Chrome's own blog says Chrome "eventually mitigated the problem by ignoring empty handlers", linking New in Chrome 112: "From Chrome 112 the service worker start and the listener dispatch ... will be omitted, if a user agent identifies that all the service worker's fetch listeners are no-ops." Sources: https://developer.chrome.com/blog/update-install-criteria, https://developer.chrome.com/blog/new-in-chrome-112. The research's recommendation (a *real* fetch handler) is correct.
7. **The Chrome push penalty windows were marked UNVERIFIED (from PushAlert). They are verified by Chrome.** "Increasing web push notification value with rate limits" (developer.chrome.com, published 2026-01-06): a rate limit of "no less than 1000 per minute" with HTTP 429 for disruptive sites; penalties of **1 day, 7 days, then 14 days**; the count resets after "42 consecutive days of non-disruptive behavior". Source: https://developer.chrome.com/blog/web-push-rate-limits.
8. **The DEP0169 fix is not PR #945.** #945 was **closed without merging** (2026-07-11, `merged_at: null`). Master no longer calls `url.parse` (it uses `new URL()` at lines 269/343 of master `src/web-push-lib.js`), so the fix landed through another commit around the 2026-07-22 ESM migration. Published 3.6.7 still calls `url.parse` (line 274). The practical conclusion is unchanged.
9. **Next.js `/sw.js` headers.** The guide sets `Cache-Control: no-cache, no-store, must-revalidate` (not plain `no-cache`), plus `Content-Type: application/javascript; charset=utf-8` and `Content-Security-Policy: default-src 'self'; script-src 'self'` on `/sw.js`. Source: https://nextjs.org/docs/app/guides/progressive-web-apps (v16.3.6, 2026-07-30). Also note that the same guide says of a custom `beforeinstallprompt` button: "we do not recommend this as it is not cross browser". That is a framing difference, not an error in our plan.
10. **`beforeinstallprompt` is no longer flagged "non-standard".** Current MDN source frontmatter has no status flags, and BCD 8.1.2 has `standard_track: true, experimental: false` (spec: WICG Manifest Incubations). It is still **not Baseline**. Support: Chrome/Chrome Android 61, Edge 79, Opera 48, Samsung Internet 8.0; Firefox and Safari have none. Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeinstallprompt_event.
11. **`launch_handler` is not "Chrome and Edge only".** BCD 8.1.2 lists Chrome/Chrome Android 110, Edge 110, Opera 96 and **Samsung Internet 21.0**. Firefox and Safari have none. Source: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/launch_handler.

## Unverified

- **"VAPID web push is not affected by the 2024 FCM legacy-API shutdown."** No Firebase or Google page states it. The migrate-v1 docs don't mention web push or VAPID. The only source is a firebase-talk thread (2024-06-04) in which a user *relays* a Google engineer's statement. It is very likely true, since Chrome subscriptions still use `fcm.googleapis.com` with VAPID, but it is not primary-sourced. The first real send in testing settles it.

1. **CONFIRMED.** Installability needs `short_name` or `name`, 192px and 512px icons, `start_url`, `display` set to fullscreen, standalone, minimal-ui or window-controls-overlay, `prefer_related_applications` absent or false, HTTPS, one click or tap, and 30 s of viewing. https://web.dev/articles/install-criteria (2024-09-19). MDN also accepts "`display` and/or `display_override`".
2. **CONFIRMED.** The SW `fetch()` requirement was dropped for menu install in Chrome 108 (mobile) and 112 (desktop). "The algorithm that displays the install prompt still requires the presence of a `fetch()` handler". https://developer.chrome.com/blog/update-install-criteria (2023-12-05).
3. **CONFIRMED.** Richer install UI: JPEG or PNG only; each side 320–3,840px; long side ≤ 2.3× the short side; identical aspect ratio per `form_factor`; eight screenshots shown; `narrow`/`wide`; description truncated after 7 lines (~324 chars); needs at least one screenshot for the form factor. https://web.dev/articles/web-apps/richer-install-ui (2026-09-16).
4. **CONFIRMED.** Maskable safe zone is a centred circle with radius = 40% of icon width. Don't use `"any maskable"`; use separate entries. https://web.dev/articles/maskable-icon.
5. **CONFIRMED.** Manifest `id` landed in Chrome 96. Without it, the id is derived from `start_url`. "Computed App Id" appears in DevTools > Application > Manifest. https://developer.chrome.com/docs/capabilities/pwa-manifest-id (2024-09-20). BCD: Safari 17 / iOS 16.4, Samsung 17.
6. **CONFIRMED.** WebAPKs are minted only by Chrome with GMS and Samsung Internet on Samsung devices. Firefox, Edge, Opera and non-GMS Chrome make browser-badged shortcuts. "Universal install" is supported by Chrome desktop and Android, Safari desktop and Edge desktop. MDN Making PWAs installable (modified 2026-09-07).
7. **CONFIRMED.** Manifest updates are checked every 24 h (up to 30 days on failure). The listed fields trigger a WebAPK update after all windows close, with the device plugged in and on Wi-Fi. Desktop "doesn't yet support changes to `icons`". https://web.dev/articles/manifest-updates (2024-09-19).
8. **CONFIRMED** (with a sourcing caveat). SamsungInternet/support#123: open, filed 2026-04-10, last comment 2026-08-31, error "Blocked dangerous app...", Chrome works on the same device. *Caveat:* the "waiting for the team" line (July 24) is a user relaying Samsung's reply on the **Samsung Developer Forum** (https://forum.developer.samsung.com/t/detail?id=10205). **Protocol (RFCs, Apple, Mozilla)**
16. **CONFIRMED.** RFC 8292: `Authorization: vapid t=<JWT>, k=<key>` (comma-separated), ES256 on P-256, `aud` = origin of the push resource, `exp` ≤ 24 h, `sub` SHOULD be `mailto:` or `https:`. "Application servers need to remember the key..." is present.
17. **CONFIRMED.** RFC 8291: `aes128gcm`, single record, "at most, 3993 octets of plaintext". *Nuance:* the "must accept 4096" rule is RFC 8030 §7.2 ("MUST NOT return a 413 ... 4096 bytes or less"); RFC 8291 says only "not required to support more than 4096".
18. **CONFIRMED.** RFC 8030: a missing TTL is a MUST-400; TTL 0 means deliver now or drop; Urgency is very-low/low/normal/high, default normal; Topic is ≤ 32 base64url chars and replaces a pending message; expired subscriptions MUST return 404; 429 MAY be returned. *Advisory:* autopush's error page asks for Topic "[A-Za-z0-9]" only, but its code accepts base64url including `-` and `_` (`autoendpoint/src/extractors/notification_headers.rs`, test `a-test-topic-which-is-just-right`), so `dm-...` is fine. Pure alphanumeric is the zero-risk choice.
19. **CONFIRMED.** Apple doc: "Don't refresh your JWT more frequently than once per hour"; stores ≤ 30 days; `PayloadTooLarge` over 4 KB; `TooManyRequests` for "too many consecutive requests to the same device token"; SNI required; ≤ 100 unacknowledged HTTP/1.1 pipelined requests; `BadJwtToken` reasons. https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers.
20. **CONFIRMED.** Apple rejects a `localhost` VAPID subject with 403 BadJwtToken: web-push #947 (closed 2026-09-11), docs PR #988 merged 2026-09-11. Apple's own page doesn't mention localhost.
21. **CONFIRMED.** Autopush: FCM-bridged data "may be limited to only 2744 bytes instead of the normal 4096 bytes"; router records expire after 60 days without check-in; TTL range 0–**2592000** (errno 112, https://mozilla-services.github.io/autopush-rs/errors.html). The research's "old docs" 30-day cap is in the current docs too. Mozilla also returns 404 or 410 for dead endpoints.
22. **CONFIRMED.** FCM quotas page (2026-09-24): 240/min and 5,000/h per device ("For Android"), 600k/min per project. It never mentions web push, so the research's UNVERIFIED on applicability stands.
