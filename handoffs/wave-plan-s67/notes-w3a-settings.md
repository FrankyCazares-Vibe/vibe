## Decisions
- route.ts: `case "theme"` follows the `chattiness` shape exactly: an unknown VALUE is a 400 "Invalid theme" (unknown KEYS are still dropped by `default`). Either way a bad client gets a failure, which the card reverts on.
- The pure view file defines its own `ThemePref` union (zero imports, so the node test loads it from its ".ts" path). It is the same three words as theme.ts's; structurally compatible.
- Status line copy for a fixed pick (not on the canvas, which shows only Auto): "Right now: Night, because you picked it." / "Right now: Light, because you picked it."
- `themePref` prop is `ThemePref | null`: null when the page's profile read failed. Then the card shows the device's `vibe_theme` (or the default) and does NOT mirror, so a failed read can't overwrite the device's choice with "light" (`mountSync` rule, tested).
- Save flow: optimistic, immediate PATCH per tap, latest-wins queue (one in flight; a tap during flight is sent after it settles; a refused save with nothing queued reverts to the last confirmed value). `{noop:true}` / no `settings.theme` in the answer = failure toast + revert (NotificationsCard rule).
- The matchMedia listener is the card's own (one listener feeds the status line's `prefersDark` AND re-applies while pref is `system`), so the only theme.ts imports are `applyTheme` (card) and `DEFAULT_THEME_PREF` (page). Fewer assumptions about the sibling's signatures.
- The mini previews use the C0 LITERAL hex values, not `var()`: they are pictures of each theme and must not flip with the page (a `var(--cream)` swatch would go near-black in Night and the "Light" tile would lie).
